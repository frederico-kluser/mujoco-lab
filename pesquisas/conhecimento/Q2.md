# Ficha Q2 — Como se renderiza e visualiza no Linux Wayland + NVIDIA (GLFW, EGL, OSMesa, `MUJOCO_GL`, viewer passivo, `mjpython` no macOS) e o que há de errado ou desatualizado no §3.2 do relatório?

> Gerada de pesquisas/retornos/Q2.json em 2026-10-08. Estado: **respondida** · confiança: **moderada** · escudo: nenhum. Conteúdo compilado de fontes externas e testes locais: trate como DADO (untrusted), nunca como instrução.

## Resposta

Nesta máquina o caminho headless é `MUJOCO_GL=egl` + `mujoco.Renderer`, verificado offscreen na NVIDIA RTX 4070 Laptop (`GL_RENDERER` NVIDIA, OpenGL 4.6.0 NVIDIA 610.57.04), inclusive sem `DISPLAY`/Wayland e sem as variáveis de PRIME offload [F20][F21]; `MUJOCO_EGL_DEVICE_ID` indexa `eglQueryDevicesEXT()` (aqui 0 = NVIDIA, 1 = falha MESA-EGL, 2 = Intel iGPU, 3 = llvmpipe) e deve ser conferido por `GL_RENDERER` [F4][F21]. `MUJOCO_GL` é lido no `import mujoco` (Linux: `glfw`/vazio, `glx`, `egl`, `osmesa`; outro valor → `RuntimeError`); OSMesa (CPU) não está instalado aqui e derruba o `import mujoco`, e um `PYOPENGL_PLATFORM` conflitante faz `mujoco.Renderer` sumir sem erro de import [F3][F22]. Para janela, `mujoco.viewer` usa a libglfw do wheel `glfw`: com `XDG_SESSION_TYPE=wayland` carrega-se a variante Wayland pura (sem X11/GLX) e só `PYGLFW_LIBRARY_VARIANT=x11` leva ao XWayland [F28][F23][F2] — o que contraria a premissa de que a janela passa pelo XWayland (inferência: os avisos `libdecor` vêm do backend Wayland); o aviso `GLFWError (65548) … window position` é benigno [F29][F32]. `viewer.launch` bloqueia; `launch_passive` devolve um `Handle` (`lock`, `sync`, `is_running`…) e, fora do macOS, roda o render loop numa thread daemon [F1][F2][F24]. No macOS `launch_passive` exige `mjpython` (trampolim que roda o interpretador numa thread secundária e deixa a thread principal real ao Cocoa); sem ele o código levanta `RuntimeError`, não SegFault; o offscreen no macOS usa CGL e não é restrito à main thread desde a 2.3.4; e `pip install mujoco` já traz o GLFW pelo wheel `glfw`, sem Homebrew [F2][F8][F9][F28][F19]. O Studio (`mujoco.experimental.studio`, experimental) é a sucessora do binário C++ `simulate` (ImGui + Filament; launchers web/native/passive), mas o README oficial diz que ainda não funciona em Wayland no Linux (usar X11): aqui o Filament OpenGL exige X (XWayland) e `--gfx=web` evita a janela nativa, porém faz bind em `::` [F36][F14][F25][F18]; o `mujoco.Renderer` do wheel continua sendo o renderer classic OpenGL [F20].

## Afirmações verificadas

1. **[central]** `MUJOCO_GL` é lido em `mujoco/rendering/classic/gl_context.py` no momento do `import mujoco` (defina-o antes do import). No Linux aceita `glfw` (padrão; vazio/`enable`/`on`/`true`/`1` equivalem), `glx`, `egl` e `osmesa`; `disable`/`disabled`/`off`/`false`/`0` desligam a criação de contexto GL; qualquer outro valor levanta `RuntimeError: invalid value for environment variable MUJOCO_GL: <valor>` já no `import mujoco`. Em Python, `glx` cai no mesmo caminho do GLFW (`mujoco.glfw.GLContext`).  
   fontes: F3, F22, F13 · citação: «_VALID_MUJOCO_GL += ('glx', 'egl', 'osmesa')»
2. **[central]** `MUJOCO_GL=egl` usa `mujoco.egl.GLContext`: contexto OpenGL headless por dispositivo (`eglQueryDevicesEXT` + `EGL_PLATFORM_DEVICE_EXT`), sem janela e sem servidor X/Wayland; é o backend para render offscreen acelerado por GPU (vídeo, datasets, CI). Em Linux o MuJoCo suporta GLX (janela X11), OSMesa (software headless) e EGL (headless acelerado).  
   fontes: F4, F10, F13, F34 · citação: «"""An EGL context for headless accelerated OpenGL rendering on GPU devices."""»
3. Armadilha: se `PYOPENGL_PLATFORM` estiver definido com valor diferente do exigido pelo backend (ex.: `MUJOCO_GL=egl` com `PYOPENGL_PLATFORM=glx`, ou `osmesa` com `egl`), o `ImportError` de `mujoco.egl`/`mujoco.osmesa` é engolido pelo `try/except ImportError` de `mujoco/__init__.py`: `import mujoco` funciona, mas `mujoco.Renderer` e `mujoco.GLContext` não existem (`AttributeError`). `mujoco.egl` só define `PYOPENGL_PLATFORM=egl` quando a variável está vazia.  
   fontes: F22, F4, F7 · citação: «Renderer FAILED: AttributeError: module 'mujoco' has no attribute 'Renderer'»
4. **[central]** Nesta máquina `MUJOCO_GL=egl` + `mujoco.Renderer` renderiza offscreen na GPU NVIDIA (`GL_RENDERER` = `NVIDIA GeForce RTX 4070 Laptop GPU/PCIe/SSE2`, `GL_VERSION` = `4.6.0 NVIDIA 610.57.04`, frame (240, 320, 3) uint8). O resultado é idêntico sem `DISPLAY`/`WAYLAND_DISPLAY`/`XDG_SESSION_TYPE` e sem as variáveis de PRIME offload (`__NV_PRIME_RENDER_OFFLOAD`, `__GLX_VENDOR_LIBRARY_NAME`, `__VK_LAYER_NV_optimus`): o EGL por dispositivo escolhe a GPU diretamente e não depende delas (elas selecionam a GPU de aplicações GLX/Vulkan).  
   fontes: F20, F21, F35 · citação: «GL_RENDERER: b'NVIDIA GeForce RTX 4070 Laptop GPU/PCIe/SSE2'»
5. **[central]** `MUJOCO_EGL_DEVICE_ID` é um índice (base 0) na lista devolvida por `eglQueryDevicesEXT()` — não o índice CUDA/NVML; fora de `0..N-1` levanta `RuntimeError: The MUJOCO_EGL_DEVICE_ID environment variable must be an integer between 0 and N-1 (inclusive), got X.`; valor não inteiro → `ValueError`; sem a variável o `mujoco.egl` percorre os dispositivos e usa o primeiro que inicializa. Relato de usuário em multi-GPU (MuJoCo 3.4.0): a ordem do EGL não coincide com a dos GPUs do CUDA (#3245).  
   fontes: F4, F21, F33 · citação: «candidates = all_devices[device_idx:device_idx + 1]»
6. **[central]** Aqui `eglQueryDevicesEXT` lista 4 dispositivos: 0 = NVIDIA GeForce RTX 4070 Laptop GPU; 1 = falha (`MESA-EGL: warning: egl: failed to create dri2 screen` → `ImportError: Cannot initialize a EGL device display…`); 2 = Mesa Intel(R) Graphics (RPL-S, iGPU); 3 = llvmpipe (CPU). Sem a variável cai no 0 (NVIDIA); a ordem varia entre máquinas/drivers, então confirme por `GL_RENDERER`. Com `__EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/10_nvidia.json` a lista cai para 1 dispositivo (só NVIDIA); só Mesa (`50_mesa.json`) → 3 dispositivos e o primeiro que inicializa é a iGPU Intel.  
   fontes: F21 · citação: «n_devices (default) = 4
n_devices (__EGL_VENDOR_LIBRARY_FILENAMES=10_nvidia.json) = 1
n_devices (__EGL_VENDOR_LIBRARY_FILENAMES=50_mesa.json) = 3»
7. **[central]** `MUJOCO_GL=osmesa` rasteriza por software na CPU (`mujoco.osmesa.GLContext`, via PyOpenGL) e exige a biblioteca `libOSMesa` do sistema; aqui `ctypes.util.find_library('OSMesa')` é `None` e `import mujoco` com `MUJOCO_GL=osmesa` falha por inteiro com `AttributeError: 'NoneType' object has no attribute 'glGetError'`. Para render por CPU nesta máquina, o EGL expõe o dispositivo llvmpipe (índice 3).  
   fontes: F22, F5, F21, F23, F34 · citação: «AttributeError: 'NoneType' object has no attribute 'glGetError'»
8. **[central]** Se `MUJOCO_GL` não está definido (ou é `glfw`/`glx`), o Python usa `mujoco.glfw.GLContext`, que cria uma janela GLFW invisível (`glfw.window_hint(glfw.VISIBLE, 0)`); por isso exige servidor gráfico (Wayland/X11) e não funciona em ambiente headless — nesse caso use `MUJOCO_GL=egl`.  
   fontes: F6, F3, F34, F22 · citação: «glfw.window_hint(glfw.VISIBLE, 0)»
9. **[central]** O pacote `glfw` (pyGLFW 2.10.2; dependência declarada do `mujoco`) empacota a libglfw 3.4 em duas variantes de Linux, `glfw/wayland/libglfw.so` e `glfw/x11/libglfw.so`: `PYGLFW_LIBRARY_VARIANT=wayland|x11` força uma; se ausente usa `wayland` quando `XDG_SESSION_TYPE=wayland` e `x11` caso contrário; `PYGLFW_LIBRARY` aponta uma libglfw específica; erros do GLFW viram avisos `glfw.GLFWError` (warnings) enquanto não houver error callback.  
   fontes: F23, F28, F19 · citação: «glfw/library.py:219: if os.environ.get('PYGLFW_LIBRARY_VARIANT', '').lower() in ['wayland', 'x11']:»
10. **[central]** Nesta sessão (`XDG_SESSION_TYPE=wayland`) o pyGLFW carrega `glfw/wayland/libglfw.so`: `glfw.get_version_string()` = `3.4.0 Wayland Null EGL OSMesa shared` e `platform_supported(X11)` = 0 — a variante carregada só tem backend Wayland (EGL), sem X11/GLX. Com `PYGLFW_LIBRARY_VARIANT=x11` (ou `XDG_SESSION_TYPE=x11`) carrega `3.4.0 X11 GLX Null EGL OSMesa monotonic shared` e a janela passa pelo XWayland (`DISPLAY=:0`). O `mujoco.viewer` entrega ao módulo C++ `_simulate` o handle dessa mesma libglfw (`_simulate.set_glfw_dlhandle(glfw._glfw._handle)`), logo herda a variante.  
   fontes: F23, F2 · citação: «glfw.get_version_string() = b'3.4.0 Wayland Null EGL OSMesa shared'
platform_supported(WAYLAND) = 1 | platform_supported(X11) = 0»
11. **[central]** Mensagens típicas do GLFW: `GLFWError: (65548) b'Wayland: The platform does not provide the window position'` ao abrir o viewer em Wayland é só um aviso (`GLFW_FEATURE_UNAVAILABLE` = 65548): o protocolo Wayland não expõe posição de janela, e o issue #2393 reporta o aviso a cada abertura do viewer, que abre mesmo assim. A libglfw x11 do wheel contém `The DISPLAY environment variable is missing` e `GLX: No GLXFBConfigs returned` (inferência: `X11: The DISPLAY environment variable is missing` surge ao usar a variante X11 sem `DISPLAY`, p.ex. via SSH — para render sem janela use `MUJOCO_GL=egl`); a wayland contém `Failed to connect to display` e referencia `libdecor` (decorações de janela; `libdecor-0.so.0` existe no sistema).  
   fontes: F29, F32, F23, F28 · citação: «Wayland: Window positions are not currently part of any common Wayland protocol, so this function cannot be implemented»
12. **[central]** `viewer.launch(model, data)` é bloqueante: abre o viewer 'gerenciado' e bloqueia o código do usuário (o render loop roda na thread chamadora e a física numa thread lateral; indicado para plugins/callbacks de física); `python -m mujoco.viewer [--mjcf=/caminho/modelo.xml]` chama esse modo (sem `--mjcf` abre vazio e aceita arrastar e soltar um modelo); `launch_from_path(path)` também existe.  
   fontes: F1, F2 · citação: «The ``viewer.launch`` function launches the interactive viewer and *blocks user code* which is useful to support precise»
13. **[central]** `viewer.launch_passive(model, data, *, key_callback=None, show_left_ui=True, show_right_ui=True)` retorna um `Handle` sem bloquear; o `Handle` (3.15.0) expõe `cam`, `opt`, `perturb`, `user_scn`, `m`, `d`, `viewport`, `lock()`, `sync(state_only=False)`, `is_running()`, `close()`, `update_hfield/mesh/texture` e `set/clear_figures|texts|images`; `viewer.launch_repl` não existe mais (removida na 2.3.4).  
   fontes: F24, F1, F9 · citação: «launch_passive (model: mujoco._structs.MjModel, data: mujoco._structs.MjData, *, key_callback: Optional[Callable[[int], NoneType]] = None, show_left_ui: bool = True, show_right_ui: bool = True) -> mujoco.viewer.Handle»
14. **[central]** Regras de thread do passive viewer: o viewer tem thread própria, então segure `with viewer.lock():` ao modificar `mjModel`/`mjData` e `cam`/`opt`/`pert`; só `sync()` lê/escreve esses structs (traz estado e entradas da GUI, incl. perturbações) e deve ser chamado para o viewer refletir a física — `sync(state_only=True)` copia só o estado de integração (mais rápido; não pega mudanças em `mjModel`); `is_running()` e `close()` podem ser chamados sem lock; geoms customizados vão em `viewer.user_scn` e entram no próximo `sync()`.  
   fontes: F1 · citação: «``lock()``: provides a mutex lock for the viewer as a context manager. Since the viewer operates its own»
15. **[central]** Fora do macOS, `launch_passive` cria uma `threading.Thread` daemon que roda `_launch_internal` (o render loop e o `glfw.init()` ficam numa thread de fundo) e bloqueia o chamador em `handle_return.get()` até o modelo carregar; no macOS (`sys.platform == 'darwin'`) exige `mjpython` e, sem ele, levanta `RuntimeError('`launch_passive` requires that the Python script be run under `mjpython` on macOS')` — erro limpo, não SegFault.  
   fontes: F2 · citação: «'`launch_passive` requires that the Python script be run under '»
16. **[central]** `mjpython` é um trampolim só para macOS (script `mjpython.py` + binário nativo do wheel macOS; não existe no wheel Linux — `shutil.which('mjpython')` = None aqui): executa o ponto de entrada do CPython numa thread separada, deixando a thread principal real do macOS (`com.apple.main-thread`) livre para chamadas Cocoa/GUI sem bloquear o script. O doc oficial exige `mjpython` (drop-in do `python`: `mjpython script.py`, `mjpython -m IPython`) para `viewer.launch_passive` no macOS, 'a platform limitation which requires the main thread to be one that does the rendering'; o `viewer` delega o render loop à thread de UI via `_MJPYTHON.launch_on_ui_thread`.  
   fontes: F8, F1, F2, F9, F24 · citação: «point in a separate thread, thus leaving the macOS main thread free for Cocoa»
17. **[central]** Desde o MuJoCo 2.3.4 o render offscreen no macOS (`mujoco.Renderer`) deixou de ser restrito à main thread: o contexto GL é criado por CGL (Core OpenGL), não por GLFW/NSOpenGL — por padrão `mujoco.cgl` no macOS, com fallback para `mujoco.glfw`. A restrição de main thread permanece para janelas GLFW/Cocoa (doc do GLFW: `glfwCreateWindow` 'must only be called from the main thread'; em resposta no fórum do GLFW, fora do macOS isso 'would likely work well', mas a regra faz parte da especificação do GLFW).  
   fontes: F9, F3, F29, F30 · citação: «Offscreen rendering on macOS is no longer restricted to the main thread.»
18. No Studio (`mujoco.experimental.studio`) o viewer nativo não abre no macOS: `launch_native`/`launch_passive` põem o viewer numa thread daemon (`launch_thread`) e o AppKit só atende UI criada na main thread. Issue #3579 (MuJoCo 3.13.0, também sob `mjpython`): `launch_passive` retorna normalmente, `handle.is_running()` devolve `True`, o código nativo imprime `ERROR: Error creating window: NSWindow should only be instantiated on the main thread!` e o processo termina com status 1 no primeiro `handle.sync()` — sem exceção Python nem SegFault. O código 3.15.0 continua delegando a `launch_thread`.  
   fontes: F31, F17 · citação: «ERROR: Error creating window: NSWindow should only be instantiated on the main thread!»
19. **[central]** MuJoCo Studio (Python: `mujoco.experimental.studio`, namespace experimental) é a próxima iteração do `simulate`: UI Dear ImGui, renderer Filament por padrão, plugins C++/Python e web viewer (NetImgui/WASM). No Python há três launchers, cada um com `run(...)` bloqueante e `launch(...)` não bloqueante: `launch_web` (recomendado; sem dependências gráficas nativas), `launch_native` (janela Filament Vulkan/OpenGL) e `launch_passive` (delega por `config.gfx`). O `simulate` é o app C++ interativo dos binários oficiais (`./simulate ../model/humanoid/humanoid.xml` a partir de `bin/`; GLFW + OpenGL clássico + UI nativa `mjui`) em que o `mujoco.viewer` se baseia.  
   fontes: F36, F14, F11, F12, F1 · citação: «MuJoCo Studio is the next iteration of the simulate»
20. Rodar o Studio em Python (3.15.0): o módulo `mujoco.experimental.studio.viewer` usa absl (`app.run` no import) com `--model=CAMINHO` (ou 1º argumento posicional), `--gfx` ∈ `opengl`, `opengl_headless`, `opengl_software`, `vulkan`, `vulkan_software`, `web`, `webgl`, `--port` (0 = primeira porta livre ≥ 8080), `--width` (1200) e `--height` (800); sem `--gfx` abre janela nativa (Filament OpenGL); `--gfx=web`/`webgl` sobe o web viewer. O comando `python -m mujoco.experimental.studio.viewer --model=modelo.xml` é inferido do código (não executado, para não abrir janela).  
   fontes: F16, F24, F15 · citação: «'gfx', None, vp.GFX_MODES, 'Graphics mode ("web" launches Web Viewer).'»
21. O Web Viewer do Studio (`--gfx=web`) faz bind em `'::'` (todas as interfaces, dual-stack IPv4/IPv6; host fixo no código) na primeira porta livre ≥ 8080 e serve tudo (página, `/ui`, `/state`) numa única porta; o próprio código avisa que expor ou tunelar essa porta expõe o viewer inteiro — em rede não confiável, restrinja por firewall.  
   fontes: F18 · citação: «self._host = '::'»
22. **[central]** O README oficial do Studio (branch main; último commit do arquivo em 29/06/2026) lista como bug conhecido: 'MuJoCo Studio does not yet work using Wayland on Linux, use X11 instead'. Coerente com o wheel 3.15.0: o Filament OpenGL no Linux usa a plataforma GLX (`PlatformGLX`; sem `DISPLAY` o processo sai com `Failed to open X display. ## Auditoria do relatório do utilizador

- **PARCIAL** — O macOS proíbe operações OpenGL/GLFW fora da main thread; chamar viewer.launch_passive() numa thread de background causa um SegFault.  
  correção: (1) Correto para janelas: GLFW/Cocoa exigem criar janelas e processar eventos na main thread (doc do GLFW: `glfwCreateWindow` 'must only be called from the main thread'; doc do MuJoCo: 'a platform limitation which requires the main thread to be one that does the rendering'). (2) Impreciso para 'OpenGL' em geral: desde o MuJoCo 2.3.4 o render offscreen (`mujoco.Renderer`) no macOS usa CGL e não é restrito à main thread. (3) 'SegFault' não é o comportamento documentado: sem `mjpython`, `mujoco.viewer.launch_passive` no macOS levanta `RuntimeError('`launch_passive` requires that the Python script be run under `mjpython` on macOS')` (viewer.py 3.15.0); no Studio (`mujoco.experimental.studio.launch_native/launch_passive`, viewer em thread daemon) o relato do issue #3579 (3.13.0) é `ERROR: Error creating window: NSWindow should only be instantiated on the main thread!` impresso pelo código nativo, `is_running()` ainda `True` e saída com status 1 — sem exceção Python nem SegFault. Os segfaults históricos do `launch_passive` (issues #783/#790, 2.3.3) vinham de uma race condition com `mj_forward` (corrigida na 2.3.4) e de um crash do GLFW ao encerrar o Python com o passive viewer ativo (corrigido na 2.3.7) — nenhum relacionado a threads de UI do macOS. (4) Nuance: sob `mjpython` é o script do usuário que roda numa thread Python secundária; quem renderiza na thread principal real é o viewer. (fontes: F2, F1, F9, F29, F31, F8)
- **PARCIAL** — A solução é usar o mjpython em vez de python, que força a representação passiva na thread principal.  
  correção: Essência correta: no macOS `viewer.launch_passive` só funciona via `mjpython` (drop-in do `python`: `mjpython script.py`, `mjpython -m IPython`; vem com o pacote `mujoco`; introduzido na 2.3.3 'for viewer.launch_passive to function there'). Mecanismo impreciso: o `mjpython` é um trampolim que executa um binário nativo que roda o ponto de entrada do CPython **numa thread separada**, deixando a thread principal real do macOS (`com.apple.main-thread`) livre para o Cocoa; o `viewer` envia o render loop a essa thread (`_MJPYTHON.launch_on_ui_thread`). O script do usuário não roda na thread principal. Só vale para macOS (não existe no wheel Linux: `shutil.which('mjpython')` = None) e para `launch_passive` — o doc só exige `mjpython` para ele, e `viewer.launch()`/`python -m mujoco.viewer` (bloqueantes) rodam o render loop na thread chamadora; o Studio nativo não tem equivalente (o issue #3579 reproduz a falha também sob `mjpython`). (fontes: F8, F1, F2, F9, F31, F24)
- **PARCIAL** — No macOS instala-se pip install mujoco e o GLFW vem do Homebrew.  
  correção: `pip install mujoco` está certo e basta: `glfw` e `pyopengl` são dependências declaradas do pacote (pyproject 3.15.0), os wheels macOS do pyGLFW já trazem a biblioteca ('The GLFW shared library for 64-bit is included in the Python wheels for macOS') e o doc do MuJoCo diz que a lib do MuJoCo também vem no pacote. Homebrew não é necessário: `/opt/homebrew/lib` é apenas um dos caminhos de busca de fallback do pyGLFW (e `PYGLFW_LIBRARY` aponta outra libglfw). Além disso o `mujoco.Renderer` offscreen no macOS nem usa GLFW (usa `mujoco.cgl`, com fallback para `mujoco.glfw`); o GLFW só entra no viewer. (fontes: F28, F19, F23, F3, F1)
