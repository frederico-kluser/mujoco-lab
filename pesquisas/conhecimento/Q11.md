# Ficha Q11 — Qual é a relação oficial entre MJX e MuJoCo Warp em 3.15, como se instalam, que limites têm face ao motor C, os números 2,33 M e 2,96 M SPS do relatório estão corretos e uma RTX 4070 de 8 GB serve?

> Gerada de pesquisas/retornos/Q11.json em 2026-10-08. Estado: **respondida** · confiança: **alta** · escudo: nenhum. Conteúdo compilado de fontes externas e testes locais: trate como DADO (untrusted), nunca como instrução.

## Resposta

Em 3.15.0 o MJX é a API JAX do MuJoCo com duas implementações — MJX-JAX (reimplementação em JAX/XLA para GPU/TPU/CPU, com autodiff) e MJX-Warp (`impl='warp'`: o MJX como frontend JAX do MuJoCo Warp; GPU NVIDIA/CUDA, CPU só para desenvolvimento; sem autodiff) — e o MuJoCo Warp (`mujoco-warp`, API nativa `mjw.*`, mantido por Google DeepMind e NVIDIA) é o motor Warp por baixo; a doc oficial chama o MJX-Warp de 'most fully-featured' e só reserva o MJX-JAX a cenas pequenas/gradientes, sem declará-lo descontinuado ou 'em manutenção' (o changelog 3.15.0 ainda altera o MJX: `mjx.render` passou a devolver `d`), e o Playground usa Warp por padrão desde a 0.2.0 [F1][F33][F4][F12][F11][F14]. Instalação: `pip install mujoco-mjx` (JAX) e/ou `pip install mujoco-mjx[warp]` (extra = só `warp-lang==1.17.0`; o mujoco_warp vai vendorizado) e/ou `pip install mujoco-warp` (3.15.0, Alpha; extras `cpu`/`cuda`=`jax[cuda12]`), mais JAX com GPU à parte — `jax[cuda13]` (recomendado pela doc do JAX; driver ≥ 580, GPU SM ≥ 7.5) ou `jax[cuda12]` (driver ≥ 525), que é o que o CI/extras do MuJoCo ainda fixam; os wheels `warp-lang` do PyPI usam CUDA 12.9 (driver ≥ 525) e o `jax` atual exige Python ≥ 3.12, requisitos que driver 610.57 + Python 3.13 satisfazem (a mistura `jax[cuda13]` + Warp CUDA 12.9 no MJX-Warp não está documentada e deve ser testada) [F1][F5][F6][F17][F24][F25][F29][F30][F28]. API: MJX `mjx.put_model`/`mjx.make_data`/`mjx.step` sob `jax.vmap`/`jax.jit`; MJWarp `mjw.put_model`/`mjw.make_data(nworld=N)`/`mjw.step(m, d)`; no Warp os buffers são fixos — `naconmax` (todos os worlds; sobrepõe `nconmax`) e `njmax` (por world, estrito) — e o estouro é comportamento indefinido sinalizado em `Data.overflow`, ao passo que o ramo JAX do MJX ignora `njmax`/`naconmax` (a 'armadilha do njmax' da SKILL.md oficial só vale para Warp); domain randomization faz-se batcheando campos do modelo (`tree_replace` + `in_axes` no MJX; `batch_sizes` no MJWarp), não reenviando modelos [F1][F3][F8][F7][F10][F15][F37][F41]. Limites frente ao motor C: float32 (C: double; `tolerance` ≥ 1e-6 no MJWarp), sem PGS/noslip, sem plugins (MJWarp: NotImplementedError; SDF só via hooks Python), sem o 'midpoint' do IMPLICITFAST, flex experimental (MJWarp) ou ausente (MJX-JAX), geoms/integradores restritos no MJX-JAX, GPU não determinística no MJWarp, e escala pior que o C em árvores únicas acima de ~60 DoF, o que dois preprints também notam [F3][F4][F8][F7][F1][F19][F35][F36]. Os números do relatório estão mal atribuídos: na tabela oficial 'SPS for MJX-Warp Graph Modes' 2,96 M é o Humanoid e 2,33 M é a cena Aloha Pot, ambos MJX-Warp via JAX FFI (modo `WARP`); o Warp puro dá 3,35 M/2,45 M, `WARP_STAGED` 2,67 M/1,96 M e recaptura forçada 0,80 M/0,65 M, sem hardware declarado; outros dados publicados: 1 humanoide a 650K (CPU M3 Max), 1,8 M (CPU 3995WX 64c), 950K (MJX-JAX em A100, batch 8192) e 2,7 M (MJX-JAX em TPU v5×8, batch 16384), saída de exemplo de 2,73 M SPS (8192 worlds) no README de benchmarks, políticas do Playground treinadas em ~10 min numa RTX 4090 com MJX-JAX e razões de aceleração sobre o MJX divulgadas pela NVIDIA (152×/313× em RTX 4090; 252×/475× em RTX PRO 6000 Blackwell) [F2][F1][F13][F34][F23][F22]. Diferenciabilidade: MJX-JAX sim ('mostly supported', mas o solver só é diferenciável em modo reverso com `opt.iterations == 1`), MJX-Warp não ('no immediate plans') e MJWarp não (issue #500; PR #1535 aberta, fora do 3.15.0) [F1][F9][F40][F3][F38][F39]. Quanto à CPU, `mujoco.rollout` é multithread e não colapsa em 4096 instâncias: medido aqui (i9-14900HX, 32 threads, máquina carregada) o humanoide rende ~34–40 K SPS com 1 thread e ~0,26–0,29 M SPS com 32, cerca de 10x abaixo dos 2,7–3,35 M SPS publicados para Warp [F20][F3][F1]. Uma RTX 4070 Laptop de 8 GB serve para aprender, desenvolver e treinar cenas tipo humanoide com milhares de worlds (estimativa própria, não medida: ~0,24–0,48 GiB de arrays declarados para 4096–8192 worlds), mas o JAX pré-aloca 75 % da VRAM (~6 GB), modos staged e cenas com malhas/CCD/muitos DoF consomem bem mais, OOMs do Warp já foram reportados e o consumo real deve ser medido com `mjwarp-testspeed --memory` [F21][F31][F32][F3][F42].

## Afirmações verificadas

1. **[central]** O MJX é a API JAX do MuJoCo para 'várias implementações': MJX-JAX (reimplementação em JAX/XLA) e MJX-Warp (o MJX como frontend JAX do MuJoCo Warp, escolhido com `impl='warp'`); `mujoco-mjx` é um pacote PyPI separado do `mujoco` (em 3.15.0 `from mujoco import mjx` falha no wheel `mujoco` sozinho).  
   fontes: F1, F33, F19 · citação: «MuJoCo XLA (MJX) provides a `JAX <https://github.com/jax-ml/jax#readme>`__ API for various implementations of MuJoCo. MJX can be found»
2. **[central]** O MuJoCo Warp (MJWarp) é mantido por Google DeepMind e NVIDIA como parte do projeto Newton; é a versão do MuJoCo para GPU NVIDIA escrita em Warp (`import mujoco_warp as mjw`); exige GPU NVIDIA para simulação rápida e aceita CPU só para desenvolvimento/depuração.  
   fontes: F4, F3 · citação: «MJWarp is maintained by [Google DeepMind](https://deepmind.google/) and [NVIDIA](https://www.nvidia.com/) as part of the [Newton](https://github.com/newton-physics/newton) project.»
3. **[central]** Na doc 3.15.0 o MJX-Warp usa o MuJoCo Warp, 'the most fully-featured implementation of MuJoCo for hardware accelerated devices'; o MJX-JAX é indicado para cenas pequenas e gradientes aproximados ('We point users to MJX-Warp otherwise'); a doc não marca o MJX-JAX como descontinuado nem 'em manutenção'.  
   fontes: F1, F2 · citação: «for a simulator that is performant for small scenes and that roughly supports gradients, MJX-JAX is a good option. We»
4. **[central]** Em 3.15.0 `mjx.put_model` sem `impl` escolhe a implementação JAX, e só escolhe Warp numa GPU CUDA se a variável de ambiente `MJX_GPU_DEFAULT_WARP` for 'true' e o `warp-lang` estiver instalado; `impl='warp'` exige `warp-lang` e GPU CUDA (ou CPU) e levanta RuntimeError sem ele.  
   fontes: F7 · citação: «os.environ.get('MJX_GPU_DEFAULT_WARP', 'f').lower() == 'true'»
5. **[central]** Instalação do MJX: `pip install mujoco-mjx`; com o backend Warp: `pip install mujoco-mjx[warp]`. O extra `warp` de mujoco-mjx 3.15.0 contém apenas `warp-lang==1.17.0` (não instala `mujoco-warp`: o código do MJWarp vem vendorizado em `mujoco.mjx.third_party.mujoco_warp`); as dependências base são absl-py, etils[epath], jax, jaxlib, mujoco>=3.15.0.dev0, scipy e trimesh, com requires-python >=3.10.  
   fontes: F1, F5, F12, F27 · citação: «pip install mujoco-mjx[warp]»
6. **[central]** JAX com GPU NVIDIA via pip: `pip install -U "jax[cuda13]"` (a doc do JAX recomenda migrar para os wheels CUDA 13) ou `"jax[cuda12]"`; o driver NVIDIA deve ser >= 580 (CUDA 13) ou >= 525 (CUDA 12) no Linux, e o wheel CUDA 13 exige GPU com SM >= 7.5; o `jax` 0.11.2 do PyPI requer Python >=3.12 e tem os extras cuda12 e cuda13.  
   fontes: F24, F29 · citação: «the driver version must be >= 525 for CUDA 12 on Linux, and >= 580 for CUDA 13 on Linux.»
7. **[central]** Os wheels `warp-lang` do PyPI são construídos com o runtime CUDA 12.9 (wheels CUDA 13.0 só no GitHub Releases); Warp com CUDA 12.x exige driver >= 525 e com CUDA 13.x >= 580; Warp suporta Python 3.10+; `warp-lang==1.17.0` publica `py3-none-manylinux_2_28_x86_64` (164,3 MB).  
   fontes: F25, F26, F30 · citação: «The binaries hosted on PyPI are currently built with the CUDA 12.9 runtime.»
8. **[central]** `pip install mujoco-warp` (3.15.0, wheel `py3-none-any`, Python >=3.10, classificador 'Development Status :: 3 - Alpha') depende de absl-py, etils[epath], mujoco>=3.12.0, numpy e warp-lang>=1.15; os extras são `dev`, `cpu` (jax) e `cuda` (`jax[cuda12]`, marcados no pyproject como temporários até o MJX:Warp).  
   fontes: F6, F28, F3 · citação: «"jax[cuda12]"»
9. **[central]** API mínima do MJX-JAX: `mjx.put_model(model)`, `mjx.make_data(mjx_model)` (ou `mjx.put_data(model, data)`) e `mjx.step(mjx_model, mjx_data)`, com o batch vindo de `jax.vmap` e `jax.jit` (as funções MJX não são JIT por omissão); `mjx.Data` é um pytree JAX atualizado com `.replace(...)`.  
   fontes: F1 · citação: «Once installed, you can use MJX by importing the ``mujoco.mjx`` package. A MuJoCo model is placed on device by calling ``mjx.put_model``,»
10. **[central]** API mínima do MJWarp: `m = mjw.put_model(mjm)`, `d = mjw.make_data(mjm, nworld=N)` (ou `mjw.put_data(mjm, mjd, nworld=N)`) e `mjw.step(m, d)` (in-place); para velocidade captura-se o passo em CUDA graph com `wp.ScopedCapture()` e `wp.capture_launch(graph)`.  
   fontes: F3, F18 · citação: «d = mjw.make_data(mjm, nworld=100)»
11. **[central]** Capacidades no MJWarp 3.15.0: `nconmax` = contatos por world (um world pode exceder se o total ≤ nworld×nconmax), `naconmax` = contatos para todos os worlds (sobrepõe `nconmax`), `njmax` = restrições por world (limite estrito); com `None`, `make_data`/`put_data` usam heurísticas por modelo. No MJX-Warp: `mjx.make_data(m, impl='warp', naconmax=..., njmax=...)`, com `naconmax` escalado pelo nº de envs do `jax.vmap`.  
   fontes: F8, F3, F1 · citação: «naconmax: Number of contacts to allocate for all worlds. Overrides nconmax.»
12. **[central]** O MJWarp usa buffers de tamanho fixo (nconmax/naconmax, njmax, nccdmax/naccdmax, nvmax, contact_sensor_maxmatch): o estouro NÃO levanta exceção, causa comportamento indefinido, é registrado por world em `Data.overflow` (bitmask `mjw.OverflowType`) e, com `Option.warn_overflow=True` (padrão), imprime avisos via `wp.printf`; `mjwarp-testspeed --overflow_behavior=error` (padrão) aborta.  
   fontes: F3, F41 · citação: «execution. When simulation demands exceed these pre-allocated limits, an overflow occurs, leading to undefined behavior.»
13. **[central]** No MJX 3.15.0 o ramo JAX de `put_data`/`make_data` ignora `njmax`/`naconmax`/`naccdmax`/`nvmax` (só `impl='warp'` os repassa) e dimensiona contatos/restrições a partir do modelo; logo a 'armadilha do njmax' da SKILL.md oficial (contatos ignorados se `njmax` for omitido em `mjx.put_data`) não se aplica a `impl='jax'`.  
   fontes: F7, F10 · citação: «return _put_data_jax(m, d, device)»
14. **[central]** O MJWarp 3.15.0 não suporta os solvers PGS e `noslip` (só CG e Newton; `put_model` levanta NotImplementedError para `noslip_iterations > 0`), nem o recurso 'midpoint' do integrador IMPLICITFAST, nem plugins de corpo/atuador/sensor (NotImplementedError); flex é experimental. Plugins SDF só existem como funções Warp injetadas em `mjw._src.collision_sdf.user_sdf`/`user_sdf_grad`.  
   fontes: F4, F8, F3 · citação: «- **Solver**: `PGS` and `noslip` not yet supported»
15. **[central]** O MJX-JAX não suporta flex (`put_model` levanta NotImplementedError), PGS/noslip (só solvers CG e NEWTON), geom SDF nem sensores PLUGIN (plugins não constam da tabela de recursos); integradores só EULER, RK4 e IMPLICITFAST; ELLIPSOID e CYLINDER só colidem com primitivos; Jacobiano só DENSE; fluido só `flInertia`; recursos não suportados fazem `put_model` levantar exceção.  
   fontes: F7, F1 · citação: «raise NotImplementedError('Flex not implemented for JAX backend.')»
16. **[central]** O MJWarp usa float32, ao contrário do `mjtNum` double do motor C (motor C verificado em 3.15.0: `qpos.dtype` float64, `tolerance` 1e-8 por omissão), e limita `tolerance` a >= 1e-6; resultados podem divergir do C (iterações, colisão, atritos pequenos) e a GPU é não determinística. O MJX-JAX deriva o dtype de `jp.zeros(1, float).dtype` (segue a configuração x64 do JAX).  
   fontes: F3, F19, F7 · citação: «MJWarp utilizes `float <https://nvidia.github.io/warp/stable/api_reference/_generated/warp.float32.html>`__s in contrast to MuJoCo's»
17. **[central]** Escala: o MJWarp escala melhor que o MJX em cenas com muitas geoms/DoFs, mas pior que o MuJoCo (C) numa única árvore cinemática grande; chega a centenas de DoFs só com `sleeping` ligado e cena particionável em islands; melhorar mecanismos únicos acima de ~60 DoFs 'remains an active priority'. Dois preprints apontam o mesmo (Isaac Lab, da NVIDIA, e SmallSatSim, de terceiros): ganhos sobre o MJX em cenas com muitos contatos e limites de escala em cenas com muitos DoF.  
   fontes: F3, F35, F36 · citação: «Improving performance for single connected mechanisms beyond ~60 DoFs remains an active priority.»
18. **[central]** Diferenciabilidade: MJX-JAX = sim ('mostly supported'); MJX-Warp = não ('does not support automatic differentiation and has no immediate plans'); MJWarp = não via autodiff do Warp (issue #500; a PR #1535 de diferenciabilidade seguia aberta quando consultada e não faz parte de 3.15.0).  
   fontes: F1, F3, F38, F39 · citação: «Note that unlike MJX-JAX, MJX-Warp does not support automatic differentiation and has no immediate plans to»
19. No MJX-JAX 3.15.0 o solver de restrições só evita `jax.lax.while_loop` quando `opt.iterations == 1`; com mais iterações o laço impede derivadas em modo reverso através de `mjx.step` (issue #2259: 'Reverse-mode differentiation does not work for lax.while_loop'), embora a busca linear use `_while_loop_scan`, compatível com reverse-mode.  
   fontes: F9, F40 · citação: «ctx = jax.lax.while_loop(cond, body, ctx)»
20. **[central]** Tabela oficial 'Steps per Second (SPS) for MJX-Warp Graph Modes': 2,96 M SPS é o Humanoid e 2,33 M SPS é a cena Aloha Pot, ambos na linha MJX-Warp via JAX FFI com graph mode `WARP`; nenhum é 'MJX (JAX)' nem 'MJWarp nativo'.  
   fontes: F2, F1 · citação: «| JAX FFI (`WARP`) | 2.96M | 2.33M |»
21. **[central]** Mesma tabela oficial: Warp puro (sem JAX FFI) = 3,35 M SPS no Humanoid e 2,45 M no Aloha Pot; `WARP_STAGED` = 2,67 M / 1,96 M; `WARP` com recaptura forçada a cada passo = 0,80 M / 0,65 M; a doc não informa o hardware.  
   fontes: F2, F1 · citação: «| Pure Warp (No JAX FFI) | 3.35M | 2.45M |»

A NVIDIA reporta (blog de 16/03/2026) que o MuJoCo Warp (MJWarp, MuJoCo 3.5) acelera o MJX em 252x (locomoção) e 475x (manipulação) numa RTX PRO 6000 Blackwell; em set/2025 eram 152x e 313x numa GeForce RTX 4090 — razões de aceleração fornecidas pelo fabricante, não SPS absolutos, e não comparáveis entre GPUs (o blog de 2025 nota que a RTX PRO 6000 acelera o MJWarp em até +44 % e o MJX em até +75 % sobre a RTX 4090).  
   fontes: F22, F23 · citação: «252x for locomotion, and 475x for manipulation tasks on the NVIDIA RTX PRO 6000 Blackwell Series.»
23. **[central]** Medido aqui (mujoco 3.15.0, i9-14900HX com 32 threads, máquina com carga ~8–13): o humanoide do benchmark MJWarp (nv=27, dt=0,005, Newton) rende ~34–40 K SPS com 1 thread e ~0,26–0,29 M SPS com `mujoco.rollout` de 32 threads (4096 trajetórias × 100 passos) — sem colapso em 4096 instâncias, mas ~10x abaixo dos 2,7–3,35 M SPS publicados para Warp (hardware não declarado).  
   fontes: F20 · citação: «rollout nbatch=4096 nstep=100 nthread=32: 259,486, 264,300, 261,720 steps/s (3 reps)»

## Auditoria do relatório do utilizador

- **CORRETA** — O MJX é uma reimplementação do motor em JAX/XLA que roda em GPU/TPU com mjx.Model/mjx.Data em batch; usam-se mjx.put_model e mjx.make_data.  
  correção: Correto para o MJX-JAX: reimplementação em JAX/XLA que roda em GPUs NVIDIA/AMD, Apple Silicon e TPUs, com `mjx.put_model(m)` + `mjx.make_data(m)` (ou `mjx.put_data(m, d)`) e `mjx.step`; o batch vem de `jax.vmap`/`jax.jit` (não é automático). Ressalvas de 3.15.0: 'MJX' passou a ser a API JAX com duas implementações (`impl='jax'`, padrão, e `impl='warp'`, GPU NVIDIA/CUDA, CPU só para desenvolvimento); TPU só vale para MJX-JAX; `mujoco-mjx` é pacote separado (F1, F7). (fontes: F1, F7)
- **PARCIAL** — O MJX-Warp/MJWarp 'otimiza operações tensoriais em chips CUDA da NVIDIA, sacrificando diferenciações analíticas'.  
  correção: Certo que é só NVIDIA/CUDA e que não é diferenciável, mas a descrição é imprecisa: MJX-Warp (`mjx.put_model(m, impl='warp')`) e MJWarp (`import mujoco_warp as mjw`) são APIs distintas sobre o mesmo motor Warp (o MJX embute uma cópia vendorizada em `mujoco.mjx.third_party.mujoco_warp`); o motor não é um compilador de operações tensoriais como o XLA/MJX-JAX: executa kernels CUDA SIMT escritos em Warp (com tiles só para álgebra linear densa, p.ex. Cholesky), com número dinâmico de contatos/restrições. Não há 'diferenciação analítica sacrificada': o MJX-JAX tem autodiff do JAX ('mostly supported'), o MJX-Warp 'does not support automatic differentiation and has no immediate plans' e o MJWarp 'não é diferenciável via Warp' (issue #500; PR #1535 aberta) (F1, F3, F12, F33, F38). (fontes: F1, F3, F12, F33, F38)
- **CORRETA** — MuJoCo CPU 'otimizado para latência' (teleoperação/MPC em tempo real).  
  correção: A doc do MJWarp diz que o MJWarp é otimizado para throughput e o MuJoCo (C) para latência (tempo de um passo); um passo do MJWarp tende a ser mais lento que um passo do MuJoCo, e o C é preferível para controle online (MPC) e interfaces interativas (F3). (fontes: F3)
- **INCORRETA** — Tabela do relatório (Humanoid): MJX (JAX) 2,33 milhões de SPS; MJWarp (CUDA/NVIDIA) 2,96 milhões de SPS.  
  correção: Os dois números existem, mas vêm da tabela 'Steps per Second (SPS) for MJX-Warp Graph Modes' da doc do MJX e ambos são MJX-Warp via JAX FFI (graph mode `WARP`): 2,96 M SPS = Humanoid; 2,33 M SPS = cena Aloha Pot (não Humanoid). O MJWarp puro (sem JAX FFI) é 3,35 M (Humanoid) e 2,45 M (Aloha Pot); `WARP_STAGED` 2,67 M/1,96 M; recaptura forçada 0,80 M/0,65 M; hardware não declarado. Não há 2,33 M para MJX-JAX no Humanoid: os valores da doc para 1 humanoide são 650K (CPU M3 Max), 1,8M (CPU AMD 3995WX 64 núcleos), 950K (MJX-JAX, A100, batch 8192) e 2,7M (MJX-JAX, TPU v5 de 8 chips, batch 16384). A frase 'sem recaptura gráfica forçada' vem da linha `WARP` vs 'forced recaptures' do próprio MJX-Warp (F2, F1). (fontes: F2, F1)
- **PARCIAL** — A versão sequencial em CPU (inclui mujoco.rollout multithread) 'estrangula' com 4096 instâncias em paralelo.  
  correção: `mujoco.rollout` não é sequencial: usa pool de threads e escala com os núcleos (a doc diz que alto throughput exige núcleos rápidos e muitas threads, e que o gargalo típico em RL é a transferência host↔device). Não há colapso em 4096: medido aqui (i9-14900HX, 32 threads, máquina carregada) o humanoide do benchmark rende ~34–40 K SPS com 1 thread e ~0,26–0,29 M SPS com 32 threads (4096×100 passos), ~10x abaixo dos 2,7–3,35 M SPS publicados para Warp; na doc, a CPU AMD 3995WX de 64 núcleos chega a 1,8 M SPS (1 humanoide) (F20, F3, F1). (fontes: F20, F3, F1)
- **PARCIAL** — Domain randomization faz-se enviando modelos com inércia/geometria diferentes via mjx.put_model.  
  correção: No MJX-JAX cria-se UM `mjx.Model` com `mjx.put_model` e randomiza-se trocando campos por arrays com dimensão de batch (`model.tree_replace({...})`, p.ex. `geom_friction`, `body_mass`, `body_ipos`, `dof_armature`) e passando `in_axes` ao `jax.vmap` (padrão do Playground: `domain_randomize(model, rng) -> (model, in_axes)`); campos numpy 'estruturais' (p.ex. `jnt_limited`) forçam recompilação se alterados. No MJWarp usa-se `mjw.put_model(mjm, batch_sizes={'dof_damping': 2})` e atribuição de arrays batcheados (índice `worldid % shape[0]`); variar malhas/geometria por mundo exige compilar cada variante no host (`spec.compile()`) e sobrescrever os campos por mundo; mudar um campo pode exigir recapturar o CUDA graph (F1, F15, F3, F18, F37). (fontes: F1, F15, F3, F18, F37)

- O hardware (GPU/CPU), nworld e versões usados na tabela 'SPS for MJX-Warp Graph Modes' (3.35M/2.96M/2.45M/2.33M) não estão na doc; a página de nightly benchmarks do MJWarp afirma listar a 'workstation', mas o texto da especificação não pôde ser recuperado.

- O consumo real de VRAM de MJWarp/MJX-Warp (com JAX) na 4070 Laptop não foi medido (nada instalado, por regra do brief); a estimativa de ~0,24–0,48 GiB para humanoide com 4096–8192 worlds vem só dos tipos declarados em types.py e exclui o workspace alocado inline (solver/CCD).
- A coexistência de `jax[cuda13]` com o wheel `warp-lang` 1.17.0 (CUDA 12.9) no mesmo processo (MJX-Warp) não está documentada; o CI/extras do MuJoCo (F17, extra `cuda` do mujoco-warp em F6, extra `cuda` do Playground em F16) fixam `jax[cuda12]`.

- A qualidade dos gradientes do MJX-JAX ('mostly supported'; issue #2259 aberta desde 2024) não foi testada; o estado da PR #1535 (diferenciabilidade do MJWarp) pode ter mudado depois da consulta.
- Não há artigo revisto por pares para MJX nem para o MuJoCo Warp; a referência acadêmica mais próxima é o preprint do MuJoCo Playground (MJX-JAX, 2025); não foi encontrado paper próprio do MuJoCo Warp.
