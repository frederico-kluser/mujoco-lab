Política neural sensor→motor com orçamento Raspberry Pi 5 na RUN

Brief do dono

Uma rede neuronal que lê os sensores e comanda todos os motores dos robôs do laboratório (Spot e Crazyflie), que caiba e corra no Raspberry Pi 5 — o limite de hardware/clock do RPi 5 aplica-se só na RUN; o treino é a poder máximo do PC (CPU + GPU, MJX/MuJoCo Warp, muitos mundos). Treino headless com métricas no terminal e um visualizador para ver a evolução da política por checkpoints.

TREINO — poder máximo

i9-14900HX (32 threads) + RTX 4070 Laptop 8 GB. CPU+GPU, MJX/MuJoCo Warp, milhares de mundos, float32 na GPU. Nada de emular latência, jitter nem atraso do RPi 5 aqui.

Única restrição que fica: a arquitetura tem de ser exportável para o orçamento RUN.

RUN — orçamento Raspberry Pi 5

4× Cortex-A76 @ 2,4 GHz, sem NPU. Export int8, shapes fixos batch=1, taxa de controlo viável, jitter do SO e térmica. Toda a validação de timing/atraso/jitter acontece aqui.

Frequências: 50–100 Hz em Python · 500 Hz em C++ · 1 kHz só com C++ + PREEMPT_RT.

Enquadramento: RUN vs TREINO — ler primeiro

O limite "poder de Raspberry Pi 5 (hardware + clock)" aplica-se apenas na RUN (deploy/inferência no device). O treino corre a poder máximo do computador; a única herança do orçamento RUN no treino é o encaixe da arquitetura (exportável: params ≤100k, ops suportadas, quantização viável).

Pipeline: treino a poder máximo → export int8/shapes fixos → validação |Δ| < 1e-3 → benchmark no device → RUN limitada ao RPi 5. A seta tracejada é o único caminho opcional de retorno.

Regras operacionais (sobrepõem-se a qualquer recomendação anterior)

  1. Não se emula latência, jitter nem atraso do RPi 5 como restrição de treino — nada de "política a 25 Hz com buffer de 200 ms" a travar o loop de treino.
  2. A validação de taxa/atraso/jitter passa para a RUN no device, depois de o modelo estar treinado e exportado.
  3. Robustez a atraso é medida opcional de deploy (treino com injeção de atraso) — só se a RUN mostrar que o loop real precisa dela.
  4. Restrições que permanecem no treino: arquitetura (MLP pequena, ops simples), shapes estáticos, quantização int8 viável, e observação/ação idênticas às que o device verá.

Regras verificadas do loop

  • Observação = data.sensordata.copy() + qpos/qvel + ação anterior. Após mj_step os campos derivados são do estado anterior → mj_forward antes de ler (atraso de 1 passo). Vistas NumPy invalidam-se a cada passo → .copy().
  • Ruído: noise= no MJCF não injeta ruído (só guarda σ) — é responsabilidade do código.
  • Ação: data.ctrl — tanh [-1,1] escalado ao ctrlrange/gear com np.clip. Ambos os robôs têm entrada única por atuador; para atuadores multi-entrada (pid/dcmotor/orientation) usar actuator_ctrladr ou lab.mjkit.Ctrl.
  • Taxa: física dt=0,002 (500 Hz); rede decide a 50–100 Hz por decimation (frame_skip 5–10). Observações normalizadas para [-1,1] com VecNormalize (guardar as estatísticas para avaliação e export).
  • Orçamento da rede: MLP densa, 2 camadas ocultas de 64–128 unidades, 10–30k parâmetros (teto 100k), saída tanh, shape de entrada fixo, batch=1, int8 (QAT nas fases finais se necessário).
loop de controlo — esqueleto (comum aos dois robôs) 
# física 500 Hz; a rede decide a cada N passos (50–100 Hz)
for t in range(n_passos):
    if t % N == 0:
        mujoco.mj_forward(m, d)                        # campos derivados atuais (senão: 1 passo de atraso)
        obs = np.concatenate([d.sensordata.copy(),     # .copy(): vistas NumPy invalidam-se
                              d.qpos[7:], d.qvel, acao_anterior])
        obs = np.clip(normalizar(obs), -1.0, 1.0)       # VecNormalize (guardar estatísticas)
        acao = np.tanh(mlp(obs))                        # [-1, 1]
        d.ctrl[:] = acao * ctrlrange                     # 12 servos (Spot) · 4 canais (Crazyflie)
    mujoco.mj_step(m, d)                                # dt = 0,002 s — só física, sem render

Orçamento Raspberry Pi 5 — aplica-se só na RUN

Conclusão do hardware: a rede corre na CPU (4× Cortex-A76); o orçamento é de CPU e de jitter, não de NPU. O AI HAT+ (Hailo-8L 13 TOPS / Hailo-8 26 TOPS) é um acelerador orientado a CNNs de visão — documenta-se rejeição de entradas 1D/vetoriais e ausência de exemplos densos; não é uma NPU para MLPs de controlo EXT.

Quantização

QuestãoResposta verificada
int8 acelera no RPi 5?Sim, ~1,83× (ResNet50V2, ORT/MLAS: 144,95 → 79,08 ms) porque o A76 tem a instrução SDOT EXT. Condição: runtime com kernel SDOT — sem dot-product (Cortex-A53, i9) o int8 fica 1,65×/1,76× mais lento.
fp16 acelera?Não — mas é limitação de software (o PyTorch CPU não implementa matmul half), não do hardware (o A76 implementa FP16 IEEE). fp16 serve para precisão/memória.
Custo em qualidadeQuaRL EXT: int8 = 8,00 % de perda em PPO/Breakout (400 → 368); erro relativo médio global 2–5 %; o paper cobre também DDPG (controlo contínuo). Benchmarks de RL quantizado são maioritariamente discretos — validar sempre a política quantizada no simulador.
EstratégiaPTQ int8 para validar depressa → QAT (torchao / TFLite converter) para o modelo final.

  • Limites MJX: max_contact_points/max_geom_pairs obrigatórios; sem warm-start; compilação no 1.º passo.

Headless — desligar o render 3D

  • mj_step/mj_forward não criam contexto gráfico (confirmado com MUJOCO_GL=disable).
  • Nunca criar mujoco.Renderer nem mujoco.viewer dentro do treino; mjkit.record sem mp4/gif/sheet só simula.
  • ⚠ MUJOCO_GL é lido no import do mujoco: osmesa quebra o import nesta máquina (falta libOSMesa) e um valor inválido dá RuntimeError no import.
  • Custo evitado: render offscreen ≈0,4 ms (320×240) e ≈1,4 ms (640×480 / 1280×720) por quadro MEDIDO vs ≈58 µs de mj_step de humanoide — renderizar no treino seria 7–24× o passo de física.
  • Armadilha: render_mode="rgb_array" no env de treino cria contexto GL e mata a velocidade sem avisar.

Riscos e mitigações

Plugin mujoco.pid aceite em silêncio pelo mjx.put_model — treina com números errados sem erro nenhum (max|Δ| ≈ 1,1e2 medido)
HIGH
Pré-checagem obrigatória (m.actuator_plugin != -1).any() — proibido em treino; rodar parity() antes de confiar. A exceção do put_model não é garantia de suporte.
Jitter do SO no RPi 5 — o pico manda, não a média (8,4–9,4 ms no kernel padrão vs ~225 µs em PREEMPT_RT sob stress; 28 µs é só uma medição de cyclictest)
HIGH
Planear por p99/max com o robô a andar e IO ativo; 50–100 Hz em Python; ≥500 Hz só em C++ e, para 1 kHz, C++ + PREEMPT_RT. Toda a validação de timing acontece na RUN.
float32 (GPU) vs float64 (CPU) — pequenas forças/fricções divergem; paridade medida é de um estado inicial, não envelope
MED
Paridade medida: Spot MJWarp ≤2,23e-06 · MJX-JAX ≤2,07e-04 · Crazyflie ≤9,44e-07 em 2 s; usar parity() por modelo e validar a política treinada no simulador antes do export.
OOM do MJX-JAX no Spot — RESOURCE_EXHAUSTED a partir de 256 mundos (6,33 GiB @256; 38,27 GiB @1024), invariante a naconmax/njmax/autotune
MED
Para o Spot usar MJWarp/MJX-Warp (e dimensionar njmax com folga: 0 overflow com nconmax 64 · njmax 256); MJX-JAX só para o Crazyflie — e ainda assim é o mais lento (37–45 K).
data.energy fica a zeros em silêncio com energia=False
LOW
Aviso nas docstrings de carregar() + 6 testes de regressão (suíte 29 passed); o default energia=True mantém os experimentos existentes exatamente iguais.
njmax subdimensionado no Spot em MJWarp — overflow NEFC em 4 de 4096 mundos sem falha visível
LOW
Dimensionar buffers com folga e vigiar Data.overflow mascarando os bits de solver (só NEFC/BROADPHASE/NARROWPHASE/CCD são estouro real).
