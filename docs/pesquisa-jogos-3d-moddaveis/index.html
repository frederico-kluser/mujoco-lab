Que jogo 3D usar como mundo visual para a nossa física?

Dossiê de escolha de um jogo 3D fácil de moddar (tipo GTA 5) que sirva de mundo + colisões + visual, enquanto a física é sempre a nossa (MuJoCo) e os modelos 3D são os nossos — para validar IA visual e automações.

Pedido original

«Pesquise com muitos subagentes e me diga que jogo 3D é fácil e podemos fazer mods tipo (GTA 5 ex) para testar nosso projeto onde no mod nós aplicaremos nossa física, mas usaremos as colisões do jogo e cenário 3D para validar a IA visual e automações no mundo real […] usaremos a nossa física, usaremos nossos modelos 3D, o jogo iremos usar apenas a solução dele e o visual.»

01

O que o jogo precisa de fornecer

A física é inteiramente nossa (mj_step) e os modelos 3D são nossos. O jogo entra só como solução pronta: um mundo 3D rico, colisões coerentes e um visual utilizável para validar IA visual (visão computacional) e automações. Cada candidato foi medido por cinco perguntas:

Física externaDá para desligar/ignorar a física do jogo e conduzir entidades com poses vindas do MuJoCo (cinemática por tick)? Qual o custo de integração?
Colisões / cenárioDá para extrair ou consultar a geometria de colisão do mundo (malhas, raycasts) para alimentar o MuJoCo com contacto real?
Visual / CVCâmara livre, captura de ecrã/vídeo, FOV/resolução e — decisivo — ground-truth para rotular dados automaticamente.
AutomaçãoScripting do mundo (tráfego, clima, NPCs), determinismo/replay, execução headless para gerar dados em lote.
Plataforma / legalRoda nesta máquina Linux (nativo ou Proton), custo, EULA permite mods, comunidade viva em 2025–2026.
02

Os 3 modos de acoplamento MuJoCo ↔ jogo

A escolha do jogo depende do modo de acoplamento. Os três convivem: um projeto pode começar no modo C e evoluir para B/A.

A

Física mestre

mj_step() → poses mod do jogo → render

O MuJoCo simula tudo; a cada tick o mod escreve posição/orientação das entidades no jogo (override cinemático). O jogo só desenha — máxima fidelidade física. Exige um hook fiável de pose por entidade.

B

Contato híbrido

colisões do jogo → geoms mj_step() → poses jogo

As colisões/raycasts reais do cenário entram como geoms no MuJoCo (ou como queries por tick). O contacto é resolvido pelo NOSSO solver — o melhor dos dois mundos. Exige API de raycast ou exportação de malhas.

C

Mundo só visual

jogo corre sozinho → imagens + ground truth → treino/validação CV

O jogo gera imagens rotuladas (poses, bboxes, semântica, profundidade) para treinar e diagnosticar modelos de visão. Sem acoplamento físico — o modo mais fácil de todos e com provas académicas.

Regra do laboratório mantida: «simulador sempre físico»

Em todos os modos, o MuJoCo é o único simulador físico: tudo passa por mj_step. O jogo recebe poses como sincronização de renderização (como o URLab faz com mocap coupling) — não há teleporte de estado físico. No modo B, as colisões do cenário entram como geoms e o contacto é resolvido pelo MuJoCo, não pelo jogo.

Arquitetura de referência (já existe em código)

  • Unreal Robotics Lab (URLab) — plugin C++ open-source (Apache 2.0) para UE 5.7 que embute o MuJoCo como backend de física e deixa o Unreal só com o rendering; acoplamento cinemático one-way (mocap), record & replay determinístico. Prova de que o padrão funciona.
  • MuJoCo Unity Plugin (oficial) — mesma filosofia: MuJoCo gere a física, a engine renderiza e acede aos dados geométricos.
  • DeepGTAV + datasets académicos (PreSIL, GTA5-seg, GTASynth, HRSD) — o GTA V já foi usado como fonte de ground-truth para ML; o paper From Gaming to Research (arXiv 2502.12303) mostra dados sintéticos comparáveis a reais em SLAM/VPR.

04

Tier A — começar por estes

Tier A · #1 Modos B + A

Garry's Mod — o melhor custo-benefício para provar o pipeline completo

É o único candidato onde os três requisitos estão prontos e documentados hoje, em Linux nativo, por ~10 €.

Prós

  • Física externa limpa: PhysObj:EnableMotion(false) neutraliza a VPhysics de vez (é assim que a Physics Gun congela objetos) + SetPos/SetAngles por tick = o MuJoCo conduz sem lutar contra o solver.
  • Colisões reais exportáveis: GetMesh()/GetMeshConvexes() devolvem a malha convexa usada pela física → geoms MuJoCo (modo B).
  • CV pronto: render.RenderView + render targets a resolução arbitrária + render.Capture (PNG/JPEG); ground-truth de poses/AABBs grátis via Lua.
  • Modding fácil: addons Lua com hot-reload, wiki completa, 20 anos de comunidade; IPC por TCP localhost ou gmsv_chttp/gmsv_websocket.
  • Linux NATIVO (ProtonDB "Native") + servidor dedicado headless via SteamCMD.

Contras

  • Visual Source 1 antigo — menos "rua real" para treinar CV de condução.
  • Captura de CV exige cliente com GPU (o render headless não está confirmado).
  • O tick do servidor limita a frequência de sincronismo: ótimo para datasets, curto para controlo fechado rápido.
  • Assets de outros jogos Source exigem esses jogos.
  • Quirks conhecidos na captura (skybox, alfa com fog — issue Facepunch #2571), contornáveis.

Como usar: modo B (colisões do jogo → geoms MuJoCo, contacto resolvido no nosso solver) com passeio em modo A (poses do mj_step escritas por tick) para a visualização.

Tier A · #2 Modo A + C

GTA V (single-player) — o mundo tipo GTA, quando o visual realista importar

O candidato "literal" do pedido: mundo urbano rico pronto + ecossistema de ferramentas maduro + o único com literatura académica provada para validar IA visual.

Prós

  • Ground-truth provado: DeepGTAV extrai por tick bboxes, segmentação, LiDAR e pose de câmara (via ZeroMQ); datasets PreSIL/GTA5-seg/GTASynth/HRSD; arXiv 2502.12303 mostra dados sintéticos comparáveis a reais em SLAM/VPR.
  • Modding fácil: ScriptHookV, ScriptHookVDotNet (C#/.NET), Menyoo (Object Spooner), CodeWalker (YMAP/YBN), Sollumz (Blender); comunidade enorme.
  • Física externa viável: natives SET_ENTITY_COORDS(_NO_OFFSET), SET_ENTITY_VELOCITY, FREEZE_ENTITY_POSITION por tick — o MuJoCo calcula, o RAGE desenha.
  • Colisões/cenário acessíveis: .ybn explora/edita no CodeWalker, importáveis no Blender via Sollumz; raycasts por natives.
  • Automação rica: hora/clima, densidade de tráfego/peds, tasks, teleporte, cenários por script.

Contras

  • Windows-only: roda em Proton/Wine (SHVDN + .NET 4.8 no prefix), mas a estabilidade sob Proton não está confirmada.
  • O solver RAGE não se desliga: é override cinemático por cima (suficiente — a física é nossa — mas não é limpo como no GMod).
  • Pipeline .ybn → geoms MuJoCo por construir (não existe pronto).
  • Sem headless oficial (não confirmado) — captura em janela.
  • Updates do jogo quebram temporariamente o ScriptHookV; OpenIV não suporta a edição Enhanced.
  • Mod Guidelines Rockstar 2026: SP não-comercial permitido, mas restrições novas (story, mapas, monetização) com aplicação a investigação interna não confirmada.

Como usar: modo A (MuJoCo manda, RAGE desenha) + modo C para gerar datasets de CV. Nunca usar GTA Online (risco de ban; o ScriptHookV fecha o jogo lá).

05

Tier B — fortes em pontos específicos

Tier B

CARLA 0.9.16

Para ground-truth pronto + determinismo + headless. Tick síncrono onde o cliente impõe pose (física externa = caminho oficial, com precedente Project Chrono), sensores CV prontos (seg/instance/depth/optical flow/bboxes), Cosmos Transfer1 + NuRec + SimReady USD para datasets, Traffic Manager, Docker headless. MIT (sobre UE EULA); a RTX 4070 8 GB serve (apertada no ramo UE5).

Contra: mundo de simulador (estradas/cidades, sem "vida" tipo GTA); build UE pesado; export de geometria do mapa não confirmado.

Tier B

BeamNG.tech + BeamNGpy

Para veículos + sensores CV prontos: câmara com RGB + profundidade + anotações ground-truth por píxel (classe/instância), LiDAR, teleporte de veículo por pose, AI traffic com regras de trânsito, import dos vossos modelos (Blender → .dae com collider). Build nativa Linux desde jan/2026 (Vulkan).

Contra: condução cinemática externa não é modo nativo (teleporte pose-a-pose com a física do jogo sempre ativa; neutralizá-la não confirmado); BeamNGpy exige BeamNG.tech (grátis académico com registo) e o binário Linux nativo do .tech não está confirmado — verificar antes de decidir.

Tier B

FiveM

Para orquestração: cenários repetíveis por resource, screenshot API (screenshot-basic), servidor autoritativo (hora/clima/tráfego), multi-cliente para testes multi-agente, servidor roda em Linux. Mesmo override cinemático do GTA V, com camada de rede/ownership.

Contra: cliente Windows-only; Platform License Agreement 2026 sob as Mod Guidelines; screenshot-basic sem commits desde 2022 (manutenção não confirmada).

Tier B

URLab (Unreal Robotics Lab)

É literalmente a arquitetura do projeto: MuJoCo mestre + UE 5.7 render, one-way kinematic coupling (mocap), record & replay determinístico, CoACD para colisões, bridge Python, Apache 2.0. Serve de referência de design para o vosso acoplamento.

Contra: alpha jovem (ICRA 2026, ~65 forks), exige desenvolvimento de plugin UE, e o cenário tem de ser montado (não vem um "GTA pronto"); evitar UE 5.8 (regressões Vulkan/Linux).

06

Tier C — nicho, só com motivo forte

Tier C

Teardown

Câmara programática (SetCameraTransform) e raycasts (QueryRaycast, GetShapeMaterialAtPosition) confirmados na API Lua; visual voxel de topo. Bom para validar pipelines de câmara/contacto. Contra: mapas pequenos, sem cidade; Proton.

Tier C

Luanti

O único com o motor aberto (dá para sincronizar MuJoCo ↔ mundo a fundo), Lua nativo, export OBJ (Meshport), headless nativo, grátis. Contra: visual voxel simples = fraco para validar IA visual realista.

Tier C

HL2 / Source SDK

Melhor extração de colisões da lista (VBSPINFO → LUMP_PHYSCOLLIDE, BSPSource → VMF) se precisarem do cenário em MuJoCo com precisão. Contra: iteração lenta (C++/Hammer/Wine) e licença Source 1 SDK não-comercial.

Tier C

KSP 1

Precedente cinemático real (mod PhysicsHold torna rigidbodies cinemáticos), modding C# maduro, Linux nativo. Contra: sem headless, mundo espacial (não urbano), docs da API desapareceram.

Tier C

Minecraft Java

Export de mundos para OBJ/USD (Mineways, jmc2obj) + MCprep no Blender; comunidade gigante; já há datasets de CV. Contra: visual blocky; EULA restritiva (não confirmado).

Tier C

ETS2 / ATS

Linux nativo (Deck Verified), SDK de telemetria oficial + injeção de inputs, tráfego AI denso, mundo rico de estradas/cidades. Contra: sem sensores CV, sem export de colisões direto.

07

Tradeoffs transversais — o que cada escolha paga

Mundo rico AAA × controlo
Jogos AAA dão ruas/interiores/tráfego orgânicos a custo zero, mas a integração física externa é sempre "por cima" (override por tick). Simuladores dão APIs oficiais e ground truth, mas mundos estéreis e curva alta. GMod fica no meio-termo: controlo de simulador com um mundo pronto de sandbox.
Desligar a física do jogo
Só o GMod (EnableMotion(false)) e engines abertas (Luanti) o fazem de vez; no GTA/BeamNG a física nativa continua a correr e há que neutralizá-la caso a caso (freeze/collision off). Como a física de verdade é a nossa, basta o jogo não "empurrar" os corpos — exequível em todos os Tier A/B.
Colisões do cenário no mj_step
Grátis no GMod (GetMesh*) e parcial no HL2 (lumps); no GTA é trabalho novo (YBN → geom); no CARLA/BeamNG usa-se raycast em vez de exportar malha — bom para contacto simples, não para contactos detalhados.
Ground truth de CV
GTA (DeepGTAV + 4 datasets) e BeamNG (anotações por píxel) ganham; GMod dá poses/AABBs "de graça" mas sem semântica pronta; CARLA dá tudo pronto (seg/instance/depth/flow).
Linux nesta máquina (RTX 4070 8 GB)
Nativo: GMod, CARLA, Luanti, ETS2, Unturned. Proton: GTA V (não confirmado estável), BeamNG.drive (nativo desde jan/2026; .tech não confirmado). Windows-only: cliente FiveM. Fora: Isaac Sim (requisitos oficiais apontam RTX 4080 mínimo / 32 GB RAM).
Legal / licenças
Source 1 SDK não-comercial (HL2); Mod Guidelines Rockstar 2026 (GTA/FiveM: SP não-comercial OK, multiplayer limitado a plataformas licenciadas); BeamNG.tech com licença académica (grátis com registo) / comercial paga; MIT/Apache nos simuladores (CARLA, URLab, Gazebo, Webots, Isaac Sim).
08

Recomendação executiva

1 · Começar pelo Garry's Mod

Montar e provar o acoplamento MuJoCo ↔ jogo (modo B, com o caminho A à mão). É onde cada peça existe documentada e corre em Linux nativo: cinemática por tick, colisões exportáveis para os vossos modelos 3D (Blender → .phy/props), captura de CV a resolução arbitrária.

2 · Em paralelo, montar o GTA V (SP)

Como alvo de validação de IA visual — o visual real só entra "caso queiras reininar um modelo de visão computacional", e aí o GTA é a escolha com provas académicas (DeepGTAV, PreSIL, GTASynth, HRSD). Atenção ao Proton e às Mod Guidelines 2026.

Se o objetivo deslizar…

…para muitos dados com rótulos prontos e determinismo, o próximo passo natural é o CARLA (sensores prontos + tick síncrono + headless). …para veículos com sensores de CV por píxel, BeamNG.tech — mas confirmar primeiro o binário Linux do .tech e a licença. …para uma integração definitiva MuJoCo + engine fotorrealista, acompanhar o URLab (ou usar o seu desenho como referência).
